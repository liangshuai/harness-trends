# 大厂技术实践简报撰写

## 适用场景

为老板撰写某技术领域（如 AICoding）的行业动态简报，要求：来源可追溯、时间在指定窗口内、格式统一、有量化干货、指引可落地但不虚构时间承诺。

简报内容分两类，可混排：
- **新闻类**：模型/产品发布、平台变更、量化报告——严格限定指定时间窗口；
- **方法论/实践类**：AI Coding 方法论与工程实践的当周动态。覆盖面按五层检索，**每周从各层挑真正有动静的主题**（有新发布、新实践、新量化结果的才收，不做概念复读；SDD、知名从业者实践等只是示例，不是固定清单）：
  1. 需求/规格层：SDD 规格驱动开发（spec-kit/Kiro）、spec 模板与验收标准工程；
  2. 执行层：agentic 工作流、subagent 编排、skills/rules 工程化、多仓工作区；
  3. 上下文层：context engineering、记忆与缓存管理、长会话压缩；
  4. 质量层：AI 代码评审、测试生成、属性测试与形式化验证；
  5. 团队层：知名团队/从业者的规模化实践（如土豆姐/Lauren Tan 类实践分享）、度量与回滚率等结果数据。
  取近一个月内新发布或新解读的材料；若主题持续演进且本周无新发布，可作为「方法论速览」条目收录，但必须标注「方法论背景，非本周新闻」，且内容要有可落地步骤。

## 核心原则

1. **时间必须核实到发布日，不能把"解读文章日期"当成"原报告日期"**。二手解读要标注"据 XX 解读"，并说明原文发布时间。
2. **格式示例只借结构，不照搬文字**。用户给的示例是占位，不能当成事实写进简报。
3. **不虚构时间承诺**。不写"本周可做""本月可做"这类未经确认的时间表；指引用"建议优先对标……""应增加……""可选取……做归因"等可执行但不绑定虚构时间的表述。
4. **每条必须有一句话简述 + 详细解读**，详细解读要分点、有数据、有可操作指引，不能文字挤成一段。
5. **指引不能虚**。"加强建设""提升能力"是废话；要写具体动作，如"将度量从 A 切换到 B""在 CI 中增加 X 检查""选取 N 个案例按四缺口归因"。
6. **只保留用户指定时间窗口内的材料**，超窗的要么剔除，要么明确标注"超窗，供参考"。

## 执行流程

### Step 1 明确边界
- 确认时间窗口（如"只要 10 月和 11 月"）
- 确认格式模板（一句话简述 + 详细解读）
- 确认是否要求量化数据、是否要求指引具体到动作

### Step 2 检索与核实
- 每条材料记录：原始报告名、发布方、**原文发布日期**、解读文章发布日期（如有）、数据来源链接或出处
- 交叉验证：同一数据在不同来源表述是否一致；不一致时标注"二手解读存在出入，建议核对原文"
- 剔除权威性不足的来源（如无官方出处的社区解读），或降级标注

### Step 3 撰写每条简报
- **一句话简述**：发布方 + 时间 + 报告名 + 核心判断（一句话讲清"这份材料说了什么、为什么值得看"）
- **详细解读**：按以下结构分点
  - ① 核心数据/判断（带数字）
  - ② 案例与量化结果（谁、做了什么、结果多少）
  - ③ 对我们的启发/指引（具体动作，不绑定虚构时间承诺）
- **补充**：原文发布时间与解读时间的区分说明；数据来源出入提示

### Step 4 自检清单
- [ ] 每条时间是否核实到发布日？解读文章和原文是否区分？
- [ ] 有没有把格式示例里的占位文字当成事实写进去？
- [ ] 有没有出现"本周可做""本月可做"等虚构时间承诺？
- [ ] 详细解读是否分点、是否有量化数据？
- [ ] 指引是否具体到动作（切换度量/增加检查/选取案例归因）？
- [ ] 超窗材料是否剔除或标注？

## 已知的坑与对策

| 坑 | 对策 |
|---|---|
| 把用户格式示例中的占位文字当成事实写入 | 格式示例只借结构；凡"计划/将/拟"类表述，必须确认有信息来源，否则不写 |
| 把解读文章日期当成原报告发布日期 | 检索时单独记录"原文发布日"和"解读发布日"，简报中注明"据 XX 解读" |
| 指引写成虚构时间表（"本周可做"） | 指引用"建议优先对标……""应增加……""可选取……做归因"等表述，不绑定虚构时间 |
| 详细解读挤成一段，老板难审阅 | 强制分点，每点一个小标题 + 数据 |
| 指引写成"加强建设" | 每条指引必须含具体动作 + 对象，如"将度量从 A 切换到 B""在 CI 中增加 X 检查" |
| 同一数据多来源表述不一致 | 标注"二手解读存在出入，建议核对原文"，不强行统一 |

## 输出模板

```
一句话简述：[发布方][日期]发布的[报告名]显示，[核心判断一句话]；[为什么值得看一句话]。
详细解读：
① 核心数据/判断：[带数字的关键结论]
② 案例与量化结果：[谁 + 做了什么 + 结果多少]
③ 对我们的启发/指引：[具体动作，如建议优先对标 X 指标、应增加 Y 检查、可选取 N 个案例做归因]
补充：[原文发布时间与解读时间的区分说明；数据来源出入提示]
```

## 紧凑模式（嵌入周报等载体时）

当简报要嵌入周报等篇幅受限的载体时，每条压缩为 **50–100 字单句**：谁 + 日期 + 事件 + 关键数字/做法 + 一句指引（「建议…」），来源 URL 附于句尾；每期 3–10 条。分点模板（一句话简述+①②③）用于独立交付的完整简报。

## 方法论/实践条目的额外要求

1. **区分个人经验与可复现方法**：从业者分享标注「实践分享」（注明作者与平台）；官方工具/框架标注版本与出处。
2. **尽量带量化**：如团队交付量、回滚率、评审时长变化；没有量化时，写清可复现的操作步骤（第一步做什么、用什么工具、在哪配置）。
3. **指引落到工程动作**：如「把需求先写成 spec 再让 agent 实现」「在 CI 中加形式化验证/属性测试关卡」「为仓库维护 RULES/CLAUDE.md 约束文件并纳入评审」。
